# Does LoRA rank matter for code generation? A controlled study

**Question.** When fine-tuning a small instruction-tuned LLM for Python code
generation with LoRA, do the adapter **rank** and the **LoRA+** learning-rate
split change *functional correctness*, measured by unit tests rather than by
text overlap?

**Setup.** `Qwen2.5-1.5B-Instruct`, fine-tuned on a decontaminated Python
instruction set, evaluated by pass@1 on **HumanEval** (164 problems) and
**MBPP-sanitized** (257 problems) with sandboxed execution.

| Configuration | Rank | α | LR ratio (B/A) |
|---|---|---|---|
| base model | - | - | - |
| `lora_r4` | 4 | 8 | 1 |
| `lora_r16` | 16 | 32 | 1 |
| `lora_r64` | 64 | 128 | 1 |
| `loraplus_r16` | 16 | 32 | 16 |

Each fine-tuned configuration is trained with **3 seeds**. α = 2r throughout,
so the LoRA scaling factor α/r = 2 is constant and rank is the only thing
changing between the plain-LoRA rows.

## Method, and the pitfalls it is designed to avoid

Fine-tuning comparisons are easy to get wrong in ways that produce confident
but meaningless tables. Each design choice below targets one such failure.

**1. Loss on response tokens only.** Labels are `-100` for every prompt,
chat-template and padding token, so the objective is the mean negative
log-likelihood of the *code* given the instruction. If prompt and padding
tokens are left in the labels, the loss is dominated by trivially predictable
positions (padding is often the EOS token) and says little about code
quality. The prompt and response are tokenized separately, so the prompt
tokens are exactly what the model sees at inference time.
(`src/lora_code/data.py`, tested in `tests/test_data.py`.)

**2. Exact token-level averaging under gradient accumulation.** Each optimizer
step divides the summed loss by the number of response tokens in the *whole*
accumulation window, not by a per-micro-batch mean, so long and short
responses are weighted correctly. (`src/lora_code/train.py`.)

**3. Functional correctness, not text similarity.** BLEU and character
similarity reward code that *looks like* the reference, and penalise a correct
solution written differently. Every response is run against the benchmark's
hidden unit tests in a separate, resource-limited process with a timeout.
"Parses as Python" is never counted as success. (`src/lora_code/execution.py`.)

**4. A base-model baseline.** Without the un-fine-tuned model evaluated under
identical prompts and decoding, a table of fine-tuned scores cannot show that
fine-tuning helped at all.

**5. Decontamination.** Training examples sharing any 13-gram with a HumanEval
or MBPP prompt or reference solution are removed before training, and
duplicates are dropped. (`data/stats.json` records how many.)

**6. Equal tuning budget.** Each configuration's learning rate is chosen from
its own 3-point grid by **validation loss** on short runs, never by benchmark
score. LoRA+ gets its own grid, because its effective learning rate on B is
16 times higher. (`scripts/sweep_lr.py`.)

**7. Uncertainty, and paired tests.** With ~160 to ~260 problems, a few problems
flipping moves pass@1 by several points, so:
- 95% CIs come from bootstrapping over problems;
- seed-to-seed SD is reported separately;
- configurations are compared *paired by problem*, with a sign-flip permutation
  test and a bootstrap CI on the difference;
- p-values are Holm-corrected across all comparisons on a benchmark.

(`src/lora_code/stats.py`, with tests that check the bootstrap's coverage and
the test's false-positive rate by simulation.)

**8. No decoding confounds.** Greedy decoding with no repetition penalty or
n-gram blocking (code legitimately repeats n-grams). Batched generation with
left padding is tested to give identical output to one-at-a-time generation.

**9. A held-out benchmark.** The benchmarks are used only for the final
evaluation. Checkpoint and LR selection use a separate validation split.

## LoRA, from scratch

The adapter is implemented directly (`src/lora_code/lora.py`) rather than
through the `peft` library:

$$y = W_0 x + \frac{\alpha}{r} B A x, \qquad A \in \mathbb{R}^{r \times d_\text{in}},\; B \in \mathbb{R}^{d_\text{out} \times r}$$

$B$ is initialised to zero, so training starts exactly at the base model. $A$ uses
the same Kaiming-uniform initialisation as `nn.Linear`. Adapters are kept in
float32 while the base model runs in bf16. LoRA+ trains $B$ with a learning rate
λ = 16 times that of $A$ (Hayou et al., 2024).

The tests check:
- the forward pass against the dense formula;
- that the wrapped model is unchanged at initialisation;
- the gradients of A and B against their closed forms;
- the trainable-parameter count against $\sum r(d_\text{in}+d_\text{out})$;
- weight merging and unmerging;
- the adapter save/load round trip.

## Reproducing

Everything runs from one Colab notebook, `notebooks/run_study.ipynb`, on a
Colab Pro GPU (A100 or L4). Or, on any CUDA machine:

```bash
pip install -e .
pytest -q                     # all checks, CPU only, under a minute
bash scripts/run_all.sh       # data -> LR sweep -> train 12 runs -> evaluate -> aggregate
```

`run_all.sh` skips any step whose output already exists, so an interrupted
session can be resumed. The individual steps are:

| Step | Command | Output |
|---|---|---|
| Data | `python scripts/prepare_data.py` | `data/train.jsonl`, `val.jsonl`, `stats.json` |
| LR sweep | `python scripts/sweep_lr.py` | `runs/selected_lr.json`, `runs/sweep_table.json` |
| Train | `python scripts/train.py --config lora_r16 --seed 0` | `runs/lora_r16/seed0/` |
| Evaluate | `python scripts/evaluate.py --run runs/lora_r16/seed0` (or `--base`) | `results/.../*.jsonl` |
| Aggregate | `python scripts/aggregate.py` | `results/summary.md`, `results/figures/` |

Per-problem results, including every raw model response and the stderr of
failed tests, are saved, so any number in the summary can be traced to
individual problems.

**Safety.** Generated code is executed. The subprocess limits contain
accidents (infinite loops, memory blow-ups, stray file writes) but are not a
security sandbox, so run evaluations in a disposable environment such as
Colab.

## Limitations

- One model family and size (1.5B). The conclusions may not transfer to larger
  models.
- One training set and one epoch. Rank may matter more with more data or longer
  training.
- pass@1 with greedy decoding. pass@k with sampling (estimator in
  `stats.pass_at_k`) is not reported.
- HumanEval and MBPP are short, self-contained function-level tasks.
